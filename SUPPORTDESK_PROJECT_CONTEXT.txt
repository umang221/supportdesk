================================================================================
SUPPORTDESK — MASTER PROJECT CONTEXT
================================================================================

DOCUMENT PURPOSE

This document is the single source of truth for the SupportDesk project.

Claude Code must read and understand this document before making substantial
changes to the project.

Do not repeatedly ask the user to explain information already contained here.

This is a portfolio project. The objective is not merely to produce working code.
The objective is to build a realistic, polished, maintainable customer-support
and SLA-management SaaS while helping the developer understand the engineering
concepts behind the system.

The developer is comfortable with JavaScript but does NOT have strong TypeScript
knowledge.

Therefore:

IMPORTANT:
- Use JavaScript, NOT TypeScript.
- Use .js and .jsx files.
- Do not introduce .ts or .tsx files.
- Do not convert the project to TypeScript.
- Explain important architectural and security decisions in beginner-friendly
  language.
- The developer should understand the system rather than blindly accepting
  generated code.

================================================================================
1. PRODUCT OVERVIEW
================================================================================

Product name:

SupportDesk

SupportDesk is a modern customer-support platform for companies to manage:

- Customer support tickets
- Conversations
- Support agents
- Teams
- Ticket assignment
- Priorities
- Statuses
- SLA policies
- SLA deadlines
- SLA breach monitoring
- Notifications
- Knowledge-base articles
- Attachments
- Customer information
- Internal notes
- Analytics
- AI-assisted ticket operations
- Audit history

The application should feel like a real B2B SaaS product rather than a
tutorial project.

The project is intended to be shown to recruiters and discussed in technical
interviews.

================================================================================
2. PRIMARY PRODUCT GOAL
================================================================================

The product should help support teams answer three questions quickly:

1. What needs attention?
2. Why does it matter?
3. What should I do next?

The main experience should therefore prioritize:

- Ticket visibility
- Conversation clarity
- Assignment
- Priority
- SLA health
- Customer context
- Fast agent actions
- Search and filtering
- Operational visibility

Do NOT design the product like a generic analytics dashboard.

The Agent Workspace is the core product experience.

================================================================================

================================================================================
14. TICKET BUSINESS RULES
================================================================================

Ticket lifecycle:

open
→ in_progress
→ pending
→ resolved
→ closed

Some transitions may be allowed depending on role and business rules.

The backend must validate state transitions.

Frontend controls alone are NOT sufficient.

Examples:

- Customer can create a ticket.
- Customer can reply to their own ticket.
- Agent can update assigned/team tickets according to permissions.
- Manager can manage team tickets.
- Admin has system-level permissions.
- Customers cannot modify another customer's ticket.
- Customers cannot modify SLA configuration.
- Customers cannot change ticket ownership arbitrarily.
- Internal notes must never be exposed to customers.

================================================================================
15. AUTHENTICATION AND AUTHORIZATION
================================================================================

Authentication answers:

"Who are you?"

Authorization answers:

"Are you allowed to do this?"

Both must be implemented correctly.

Never trust:

- user IDs
- roles
- permissions
- ownership
- ticket IDs
- team IDs

sent from the client.

The server must determine the authenticated user from the secure session.

The server must check authorization before sensitive operations.

Passwords must never be stored in plaintext.

Use a strong password hashing algorithm such as bcrypt or Argon2.

Use secure HTTP-only cookies where appropriate.

Do not expose secrets to the frontend.

================================================================================
17. DATABASE AND PERFORMANCE
================================================================================

Use indexes where query patterns justify them.

Likely indexed fields include:

- ticket number
- ticket status
- priority
- assignee
- customer
- team
- SLA deadline
- createdAt
- updatedAt
- email where appropriate

Avoid unnecessary database queries.

Do not load thousands of tickets into the browser at once.

Use server-side filtering/searching where appropriate.

Do not optimize blindly.

Measure or reason about the actual bottleneck first.

================================================================================
18. REDIS AND BACKGROUND JOBS
================================================================================

Redis may be used for:

- Caching
- Queues
- Rate limiting
- Temporary state

BullMQ should handle background work such as:

- SLA monitoring
- Email sending
- Notifications
- AI processing
- Scheduled maintenance jobs

Do not perform expensive background work synchronously during normal API
requests when it can reasonably be queued.

Example:

User creates ticket
→ ticket saved
→ background jobs queued
→ API responds
→ worker processes email/AI/etc.
